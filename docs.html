1. Getting started

  1. Start on the AWE homepage to understand the ecosystem.
  2. Open Products to choose a website or code repository.
  3. Use the product's own interface and follow its on-page instructions.
  4. For code, read the repository README, inspect the default branch and review setup instructions before installing dependencies.
  5. When reporting an issue, include the page or command, expected behavior, actual behavior, browser/OS, and reproducible steps. Never include passwords, API keys or private tokens.
Discover → Read docs → Try safely → Report / contribute

5. Playground guide

The AWE Playground supports HTML, CSS and JavaScript prototyping in your browser. Choose a file, edit the code, run a preview and download an HTML artifact. The preview is sandboxed and client-side.

  • Run preview: applies the current editor contents.
  • Choose a file: reads a selected local file in your browser.
  • Download HTML: exports the current HTML/CSS/JS draft.
  • Language mode: JSON and text are displayed; Python, Rust, C++ and other compiled/server languages need an external runtime.

6. Troubleshooting

A page is blank or styles are missing

Refresh, check the URL, inspect browser developer tools and verify that asset paths match the hosting base path. GitHub Pages project sites often need relative asset paths; root paths beginning with / may point to the domain root.

A button does nothing

Confirm the expected feature is implemented, check the browser console, and test without extensions. A visual control alone does not guarantee a connected backend.

A build fails

Read the first meaningful error, check the runtime version, install dependencies using the repository's documented lockfile command, and run formatting, linting, unit tests and an actual app smoke test.

Login, API or network errors

Check configuration and service availability. Never publish tokens in issues or commit secrets into source control.

7. Contribute safely

  1. Fork the repository or create a feature branch.
  2. Read existing architecture and conventions before changing files.
  3. Make a focused change and document user-visible behavior.
  4. Run formatting, static checks, tests and a manual smoke test.
  5. Open a pull request with a concise summary, evidence and known limitations.

Documentation rule: label implemented features, planned ideas and experimental behavior separately. Avoid promises such as “100% secure” or “always online” without measurable evidence.
